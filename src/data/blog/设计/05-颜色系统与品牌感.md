## 前置知识与学习目标

**前置知识：** 已有稳定的排版和间距层级，能区分主操作、状态与辅助信息。

**本篇唯一核心问题：** 怎样让颜色承担语义而不是制造视觉噪声？

读完后，你应该能够：建立中性色、品牌色和语义色的职责边界，并验证对比度和跨主题表现。本篇沿用“跨端客户工单管理 SaaS”，核心对象统一为 `ticket`、`customer`、`assignee`、`status`、`priority` 与 `permission`。

上一章已经解决“怎样用字体层级、行高和间距建立稳定的阅读节奏”的问题；本篇把它作为输入，不再重复完整解释。

## 从真实问题出发

工单页面同时用蓝、紫、橙强调按钮、状态和卡片，用户无法判断颜色代表操作还是风险。

先不要急着选择组件或颜色。应先写清楚当前用户、对象、触发条件、成功结果和失败后仍需保留的上下文，再判断界面应该表达什么。

## 核心机制

颜色系统先分角色再选色值。中性色建立层级，品牌色建立识别，语义色表达成功、警告、错误和信息。颜色不能成为唯一线索，状态还要由文字、图标或结构表达。

### 1. 主操作使用单一 action token，链接、选中态和焦点态保持可解释关系

主操作使用单一 action token，链接、选中态和焦点态保持可解释关系。它先固定主路径和优先级，后续布局不得反过来改变业务判断。验收时要用真实任务观察用户能否找到下一步。

### 2. 状态色按语义命名，不按具体色名命名，避免主题切换时含义漂移

状态色按语义命名，不按具体色名命名，避免主题切换时含义漂移。它把抽象原则转换成可见结构。验收时应检查对象、标签、状态和操作是否逐项对应，而不是凭整体观感打分。

### 3. 文本、图标和边框分别检查对比度，不能只检查品牌主色

文本、图标和边框分别检查对比度，不能只检查品牌主色。它负责异常与边界，必须使用空数据、慢请求、权限差异或冲突数据复测，不能只验证理想状态。

### 4. 亮色与暗色主题分别映射语义 token，而不是对现有色值机械反相

亮色与暗色主题分别映射语义 token，而不是对现有色值机械反相。它防止局部页面自行发明规则。跨端、跨主题或跨角色检查时，语义保持一致，呈现方式才允许重组。

## 关键角色、数据与状态

| 项目     | 在本篇中的含义                                                                       |
| -------- | ------------------------------------------------------------------------------------ |
| 输入     | 输入是语义角色和显示背景                                                             |
| 业务对象 | `ticket` 是工单，`customer` 是客户，`assignee` 是当前负责人                          |
| 约束     | `permission` 决定可执行动作；`priority` 影响排序，不直接替代业务状态                 |
| 状态主线 | `draft → submitted → processing → resolved → closed`，只有满足权限和前置条件才能转换 |
| 输出     | 是跨组件、跨主题一致的颜色规则。                                                     |

输入是语义角色和显示背景；中间状态是调色板、token 映射和对比度测试；输出是跨组件、跨主题一致的颜色规则。

## 最小实践：贯穿工单案例

`status=processing` 使用信息色并显示“处理中”，`priority=urgent` 使用风险色并保留文字；主按钮只使用 `color-action-primary`。

执行时使用下面的决策记录，避免示例只有结果而没有中间状态：

```text
输入：角色、ticket、当前 status、permission、终端与网络状态
检查：核心任务、业务规则、可见反馈、失败恢复、跨端差异
中间状态：记录用户动作、系统判断、状态变化和仍被保留的数据
输出：可验证的界面方案、实现约束与验收证据
失败边界：权限不足、空数据、超时、冲突、长文案和窄屏
```

这里的 `status` 表示业务状态；请求的 loading/error 是界面请求状态，两者不能混为一个字段。示例中的数值与规则只用于教学，接入真实项目时必须由产品规则、接口契约和数据字典确认。

## 常见误区

- **用品牌色填满所有重点：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **成功与可点击都使用绿色：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **只用红绿区分两类数据：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。

## 适用边界与不适用场景

- 数据可视化的分类色与连续色需要独立色板，不能直接复用按钮色。
- 品牌活动可临时扩展色彩，但业务状态 token 不随活动改变。

如果当前任务没有多对象关系、状态变化或失败恢复，不要为了套用本章而制造额外组件和流程。复杂度必须来自真实认知问题。

## 本篇总结

建立中性色、品牌色和语义色的职责边界，并验证对比度和跨主题表现。真正的完成标准不是“看起来合理”，而是每条规则都能追溯到任务、数据、状态或规范，并能通过边界场景验证。
