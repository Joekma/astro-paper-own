## 前置知识与学习目标

**前置知识：** 理解对象列表、筛选和界面状态。

**本篇唯一核心问题：** 怎样让数据表格支持比较、定位和批量行动，而不是堆满字段？

读完后，你应该能够：能按任务设计字段顺序、密度、选择模型、操作和移动端替代方案。本篇沿用“跨端客户工单管理 SaaS”，核心对象统一为 `ticket`、`customer`、`assignee`、`status`、`priority` 与 `permission`。

上一章已经解决“怎样把加载、空、错误、权限和成功反馈建模为可恢复的界面状态机”的问题；本篇把它作为输入，不再重复完整解释。

## 从真实问题出发

工单表格有二十多列，客服横向滚动后仍找不到应优先处理的对象。

先不要急着选择组件或颜色。应先写清楚当前用户、对象、触发条件、成功结果和失败后仍需保留的上下文，再判断界面应该表达什么。

## 核心机制

表格适合比较同构对象。列顺序应从识别、判断到行动；排序改变顺序，筛选改变集合，分页改变视窗，选择集必须明确跨页规则。

### 1. 第一屏保留对象标识、关键状态、优先级、负责人和时效

第一屏保留对象标识、关键状态、优先级、负责人和时效。它先固定主路径和优先级，后续布局不得反过来改变业务判断。验收时要用真实任务观察用户能否找到下一步。

### 2. 数值按小数位和单位对齐，状态列使用文字加视觉标记

数值按小数位和单位对齐，状态列使用文字加视觉标记。它把抽象原则转换成可见结构。验收时应检查对象、标签、状态和操作是否逐项对应，而不是凭整体观感打分。

### 3. 行级操作只保留高频安全动作，其余进入菜单；危险动作不与普通动作并列

行级操作只保留高频安全动作，其余进入菜单；危险动作不与普通动作并列。它负责异常与边界，必须使用空数据、慢请求、权限差异或冲突数据复测，不能只验证理想状态。

### 4. 移动端改为摘要卡与详情下钻，不把完整表格缩到不可读

移动端改为摘要卡与详情下钻，不把完整表格缩到不可读。它防止局部页面自行发明规则。跨端、跨主题或跨角色检查时，语义保持一致，呈现方式才允许重组。

## 关键角色、数据与状态

| 项目     | 在本篇中的含义                                                                       |
| -------- | ------------------------------------------------------------------------------------ |
| 输入     | 输入是字段、比较任务和数据规模                                                       |
| 业务对象 | `ticket` 是工单，`customer` 是客户，`assignee` 是当前负责人                          |
| 约束     | `permission` 决定可执行动作；`priority` 影响排序，不直接替代业务状态                 |
| 状态主线 | `draft → submitted → processing → resolved → closed`，只有满足权限和前置条件才能转换 |
| 输出     | 是可扫描、可恢复的表格交互。                                                         |

输入是字段、比较任务和数据规模；中间状态是列优先级、查询状态和选择集；输出是可扫描、可恢复的表格交互。

## 最小实践：贯穿工单案例

客服按 SLA 剩余时间排序并选择当前页 20 条工单；批量分派确认框明确“仅当前页 20 条”，完成后保留筛选并刷新受影响行。

执行时使用下面的决策记录，避免示例只有结果而没有中间状态：

```text
输入：角色、ticket、当前 status、permission、终端与网络状态
检查：核心任务、业务规则、可见反馈、失败恢复、跨端差异
中间状态：记录用户动作、系统判断、状态变化和仍被保留的数据
输出：可验证的界面方案、实现约束与验收证据
失败边界：权限不足、空数据、超时、冲突、长文案和窄屏
```

这里的 `status` 表示业务状态；请求的 loading/error 是界面请求状态，两者不能混为一个字段。示例中的数值与规则只用于教学，接入真实项目时必须由产品规则、接口契约和数据字典确认。

## 常见误区

- **默认展示所有字段：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **把排序图标当作当前排序说明：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **跨页全选却不说明影响范围：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。

## 适用边界与不适用场景

- 异构内容或以浏览为主时应使用列表或卡片。
- 超大数据集必须采用服务端查询，不能把全部数据加载到浏览器再分页。

如果当前任务没有多对象关系、状态变化或失败恢复，不要为了套用本章而制造额外组件和流程。复杂度必须来自真实认知问题。

## 本篇总结

能按任务设计字段顺序、密度、选择模型、操作和移动端替代方案。真正的完成标准不是“看起来合理”，而是每条规则都能追溯到任务、数据、状态或规范，并能通过边界场景验证。
