## 前置知识与学习目标

**前置知识：** 理解信息层级、颜色、排版和组件约束。

**本篇唯一核心问题：** 怎样围绕高频业务任务组织一个专业、可恢复的后台页面？

读完后，你应该能够：能把标题、筛选、数据、操作和反馈组成稳定的后台任务路径。本篇沿用“跨端客户工单管理 SaaS”，核心对象统一为 `ticket`、`customer`、`assignee`、`status`、`priority` 与 `permission`。

上一章已经解决“怎样把视觉决策编码为 Design Tokens 和受约束组件，使 AI 输出不再漂移”的问题；本篇把它作为输入，不再重复完整解释。

## 从真实问题出发

客服每天处理数百条工单，但页面把欢迎语、统计卡、筛选和按钮都放在同一视觉层级。

先不要急着选择组件或颜色。应先写清楚当前用户、对象、触发条件、成功结果和失败后仍需保留的上下文，再判断界面应该表达什么。

## 核心机制

后台页面的价值是让用户查找、判断、操作和恢复。页面级操作靠近标题，对象级操作靠近对象，批量操作只在选择后出现；反馈必须保留上下文，让失败不会迫使用户重做。

### 1. 页头回答当前位置、对象范围和页面级动作

页头回答当前位置、对象范围和页面级动作。它先固定主路径和优先级，后续布局不得反过来改变业务判断。验收时要用真实任务观察用户能否找到下一步。

### 2. 筛选条件可见、可清除、可分享，结果区反馈命中数量

筛选条件可见、可清除、可分享，结果区反馈命中数量。它把抽象原则转换成可见结构。验收时应检查对象、标签、状态和操作是否逐项对应，而不是凭整体观感打分。

### 3. 高频字段与操作前置，低频详情进入抽屉或详情页

高频字段与操作前置，低频详情进入抽屉或详情页。它负责异常与边界，必须使用空数据、慢请求、权限差异或冲突数据复测，不能只验证理想状态。

### 4. 危险操作说明对象数量、不可逆影响和恢复策略

危险操作说明对象数量、不可逆影响和恢复策略。它防止局部页面自行发明规则。跨端、跨主题或跨角色检查时，语义保持一致，呈现方式才允许重组。

## 关键角色、数据与状态

| 项目     | 在本篇中的含义                                                                       |
| -------- | ------------------------------------------------------------------------------------ |
| 输入     | 输入是用户角色、对象和任务频率                                                       |
| 业务对象 | `ticket` 是工单，`customer` 是客户，`assignee` 是当前负责人                          |
| 约束     | `permission` 决定可执行动作；`priority` 影响排序，不直接替代业务状态                 |
| 状态主线 | `draft → submitted → processing → resolved → closed`，只有满足权限和前置条件才能转换 |
| 输出     | 是可在正常和异常状态下完成任务的列表或详情页。                                       |

输入是用户角色、对象和任务频率；中间状态是页面骨架与操作层级；输出是可在正常和异常状态下完成任务的列表或详情页。

## 最小实践：贯穿工单案例

客服打开“待处理工单”，筛选 `priority=urgent`，批量分派给 `assignee=Li`；失败时保留选择集和筛选，并提供重试。

执行时使用下面的决策记录，避免示例只有结果而没有中间状态：

```text
输入：角色、ticket、当前 status、permission、终端与网络状态
检查：核心任务、业务规则、可见反馈、失败恢复、跨端差异
中间状态：记录用户动作、系统判断、状态变化和仍被保留的数据
输出：可验证的界面方案、实现约束与验收证据
失败边界：权限不足、空数据、超时、冲突、长文案和窄屏
```

这里的 `status` 表示业务状态；请求的 loading/error 是界面请求状态，两者不能混为一个字段。示例中的数值与规则只用于教学，接入真实项目时必须由产品规则、接口契约和数据字典确认。

## 常见误区

- **把后台做成营销首页：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **所有操作长期展示：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。
- **保存失败后清空输入和选择：** 这会让界面结论失去可验证依据；应回到输入、状态和恢复路径重新检查。

## 适用边界与不适用场景

- 面向偶发访客的自助页面应降低密度，不照搬内部后台。
- 实时监控场景需要专门的刷新、告警与时间语义。

如果当前任务没有多对象关系、状态变化或失败恢复，不要为了套用本章而制造额外组件和流程。复杂度必须来自真实认知问题。

## 本篇总结

能把标题、筛选、数据、操作和反馈组成稳定的后台任务路径。真正的完成标准不是“看起来合理”，而是每条规则都能追溯到任务、数据、状态或规范，并能通过边界场景验证。
