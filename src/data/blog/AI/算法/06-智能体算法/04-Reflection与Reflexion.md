## 学习导航

**核心问题**：如何把模型的不确定决策放进可控制、可审计的运行循环？本文聚焦“Reflection 与 Reflexion”。

**贯穿场景**：一个研究型 Agent 需要检索资料、调用工具、修正计划并在预算内结束。

读完本文，你应该能够：

- 用输入、输出和不变量解释“Reflection 与 Reflexion”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

Reflection 是基于结果生成改进意见的通用过程；Reflexion 进一步把反馈写入可复用的语言记忆，用于后续尝试。

评估“Reflection 与 Reflexion”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 运行状态与动作契约

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 用户目标、结构化状态、可用工具、预算和安全策略     |
| 输出     | 动作、观察、状态更新、最终结果或明确终止原因       |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“Reflection 与 Reflexion”设计实现前，至少回答四个问题：

1. 当前目标、事实和未完成步骤分别是什么？
2. 模型可以建议哪些动作，运行时禁止哪些动作？
3. 工具副作用如何审批、幂等和审计？
4. 成功、等待、取消和预算耗尽如何区分？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 一次 Agent 决策推演

理解“Reflection 与 Reflexion”可以按下面顺序：

1. **组装受控状态**：只提供当前任务需要且有来源的上下文。
2. **产生结构化动作**：模型从允许动作集合中给出参数化意图。
3. **执行并观察**：运行时校验后调用工具，把真实结果写回。
4. **判断终止**：根据验收事实和预算继续、等待或结束。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

第一次查询过宽导致无关结果，反馈写成“保留产品名并增加年份过滤”，第二次按可执行规则重试。

推演“Reflection 与 Reflexion”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“Reflection 与 Reflexion”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“Reflection 与 Reflexion”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 预算、副作用与终止

没有外部验证的自我批评可能只是另一段幻觉；无限反思会增加成本而不改善结果。

Agent 成本随模型调用、工具调用和循环步骤累积；任何反思、委派或搜索策略都应报告单位成功任务成本。

本文场景至少应观察：任务成功率、步骤数、工具错误、恢复次数、成本和停止原因。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“Reflection 与 Reflexion”接入 AI 系统时，建议分为三层：

1. **模型**：负责不确定的理解、候选与内容生成。
2. **运行时**：负责权限、工具、状态、取消与恢复。
3. **评估器**：根据终态和轨迹证据判定成功及风险。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 轨迹和任务验收

对每条反馈记录证据、修改项、前后指标、尝试次数和是否跨任务复用。

“Reflection 与 Reflexion”的最小测试集应覆盖：

- 无效工具与参数；
- 提示注入式工具结果；
- 重复副作用调用；
- 工具超时和部分成功；
- 最大步骤与人工拒绝；
- 检查点恢复后的下一动作。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。

## 总结与下一篇

- Reflection 是基于结果生成改进意见的通用过程；Reflexion 进一步把反馈写入可复用的语言记忆，用于后续尝试。
- 正确实现必须同时定义输入输出、关键状态、失败行为和资源上限。
- 先用小数据验证不变量，再扩大规模衡量质量、延迟、成本和内存。
- AI 工程中的模型决策与真实执行应分层，避免把候选意图当作已完成事实。
