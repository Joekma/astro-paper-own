## 学习导航

**核心问题**：如何减少重复工作，又不让陈旧数据、重试和降级破坏正确性？本文聚焦“TTL 缓存与失效策略”。

**贯穿场景**：一个 RAG/Agent 服务需要缓存模型与检索结果，并安全处理工具调用失败。

读完本文，你应该能够：

- 用输入、输出和不变量解释“TTL 缓存与失效策略”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

TTL 定义条目可复用时间，失效策略决定过期是读取时惰性删除、后台清理还是主动刷新。

评估“TTL 缓存与失效策略”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 请求、缓存与失败契约

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 请求、缓存键、有效期、失败类型和重试预算           |
| 输出     | 命中结果、真实执行结果、降级响应或明确错误         |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“TTL 缓存与失效策略”设计实现前，至少回答四个问题：

1. 缓存或去重键包含哪些语义与版本？
2. 失败是瞬时、永久还是结果未知？
3. 重复执行是否安全以及记录保留多久？
4. 降级结果的新鲜度和能力差异怎样暴露？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 命中或失败路径推演

理解“TTL 缓存与失效策略”可以按下面顺序：

1. **识别请求**：生成规范化键、幂等键或内容版本。
2. **尝试主路径**：在统一截止时间与容量限制内执行。
3. **按失败分类响应**：选择命中、重试、熔断、回退或明确失败。
4. **记录结果**：保存首次结果、状态、年龄和后续恢复信息。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

政策缓存 TTL=10 分钟，过期后首个请求回源；加入随机抖动可避免大量键同一时刻失效。

推演“TTL 缓存与失效策略”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“TTL 缓存与失效策略”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“TTL 缓存与失效策略”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 陈旧、重试与降级边界

TTL 不是数据正确性的充分条件；太长返回陈旧值，太短造成回源风暴，删除源数据也需主动失效。

可靠性模式会消耗额外存储、延迟和流量；必须同时衡量命中收益、陈旧风险与故障时的放大系数。

本文场景至少应观察：命中率、陈旧率、重复执行率、重试放大、熔断状态和恢复时间。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“TTL 缓存与失效策略”接入 AI 系统时，建议分为三层：

1. **键与状态层**：保存版本、有效期、幂等状态和首次结果。
2. **策略层**：依据失败分类与预算组合可靠性模式。
3. **观测层**：暴露命中、重试放大、熔断和降级影响。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 可靠性演练

记录 age、ttl、stale 状态、回源延迟、同刻过期数量和刷新失败。

“TTL 缓存与失效策略”的最小测试集应覆盖：

- 缓存命中与过期；
- 重复进行中和重复成功；
- 永久错误不重试；
- 瞬时错误带抖动重试；
- 熔断探测与恢复；
- 降级数据过旧或权限变化。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。
