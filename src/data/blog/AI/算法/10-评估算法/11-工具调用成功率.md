## 学习导航

**核心问题**：如何把“效果更好”改写成可复现、可解释且能指导发布的证据？本文聚焦“工具调用成功率”。

**贯穿场景**：一个 RAG/Agent 版本同时改变检索、提示词和工具策略，需要判断是否可以上线。

读完本文，你应该能够：

- 用输入、输出和不变量解释“工具调用成功率”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

工具调用成功率应分解为选择正确、参数合法、授权通过、执行成功、结果可用和副作用正确，而非只看 HTTP 状态。

评估“工具调用成功率”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 样本、标签与指标口径

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 评估样本、真实标签、系统输出、轨迹和评分规则       |
| 输出     | 指标、置信信息、分层诊断和发布结论                 |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“工具调用成功率”设计实现前，至少回答四个问题：

1. 样本、标签、预测和评分单位是什么？
2. 分母为零、无答案和弃权怎样计分？
3. 宏平均、微平均或查询平均回答什么问题？
4. 指标变化是否超过抽样方差并具有业务意义？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 逐样本计算示例

理解“工具调用成功率”可以按下面顺序：

1. **锁定口径**：冻结数据版本、评分规则、K、阈值和切片。
2. **逐样本计算**：保留中间量与失败类型，不先求平均。
3. **聚合与估计不确定性**：报告样本数、分布、区间和分群差异。
4. **形成决策**：将质量与安全、成本、延迟护栏一起用于发布。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

选对 search 但 query 为空属于参数失败；返回 200 但结果 Schema 错误仍不可供 Agent 使用。

推演“工具调用成功率”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“工具调用成功率”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“工具调用成功率”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 统计解释与指标盲区

重试后的最终成功会掩盖首次失败和成本；业务拒绝不应总算基础设施错误。

评估成本包括标注、Judge、实验流量和人工复核；更便宜的代理指标只有在与目标指标稳定相关时才可替代。

本文场景至少应观察：质量指标、样本量、方差、分群差异、成本和延迟。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“工具调用成功率”接入 AI 系统时，建议分为三层：

1. **离线集**：用于快速回归、分层诊断和失败复现。
2. **在线实验**：验证真实行为、长期效应和业务指标。
3. **发布门禁**：组合主指标、护栏、样本量与人工豁免。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 评估集和发布验收

按阶段统计 attempt success、eventual success、参数错误、权限拒绝、延迟和重复副作用。

“工具调用成功率”的最小测试集应覆盖：

- 可手算的小样本；
- 分母为零或无相关项；
- 同分和截断边界；
- 类别或任务极不平衡；
- 不同随机种子或 Judge 重复评分；
- 关键业务切片退化。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。

## 总结与下一篇

- 工具调用成功率应分解为选择正确、参数合法、授权通过、执行成功、结果可用和副作用正确，而非只看 HTTP 状态。
- 正确实现必须同时定义输入输出、关键状态、失败行为和资源上限。
- 先用小数据验证不变量，再扩大规模衡量质量、延迟、成本和内存。
- AI 工程中的模型决策与真实执行应分层，避免把候选意图当作已完成事实。
