## 学习导航

**核心问题**：如何从语料中召回真正相关的证据，并知道相关性在哪一层丢失？本文聚焦“交叉编码器重排序”。

**贯穿场景**：一个企业 RAG 系统需要同时处理精确术语、自然语言问题和权限过滤。

读完本文，你应该能够：

- 用输入、输出和不变量解释“交叉编码器重排序”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

交叉编码器把 query 与 document 联合编码并输出相关性分数，通常比双编码器精细但计算成本更高。

评估“交叉编码器重排序”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 查询、语料与候选契约

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 查询、文档语料、索引、过滤条件和召回数量           |
| 输出     | 带文档标识、分数和来源信息的有序候选               |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“交叉编码器重排序”设计实现前，至少回答四个问题：

1. 查询与文档经过了哪些规范化和分词？
2. 相关文档是否确实存在于语料和索引？
3. 分数、距离和排序方向是否一致？
4. 过滤、召回和重排各自截断多少候选？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 检索链路推演

理解“交叉编码器重排序”可以按下面顺序：

1. **准备查询**：解析意图、字段与权限，保留原始查询。
2. **生成候选**：从一个或多个索引取回带来源的候选。
3. **融合或重排**：在明确分数语义下去重、排序和截断。
4. **交付证据**：返回可定位原文、版本和分数的上下文。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

先由 ANN 召回 50 篇，再让交叉编码器逐对评分并取前 5；它能利用查询词与文档词的细粒度交互。

推演“交叉编码器重排序”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“交叉编码器重排序”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“交叉编码器重排序”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 召回质量与系统成本

重排序无法找回未召回文档；候选过多会放大模型成本，分数也未必是校准概率。

检索成本要分成索引构建、候选搜索、重排和上下文 Token；质量则至少区分语料覆盖、召回与排序。

本文场景至少应观察：Recall@K、NDCG、候选覆盖率、过滤损失、延迟和索引成本。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“交叉编码器重排序”接入 AI 系统时，建议分为三层：

1. **索引层**：保证文档、切块、元数据和向量版本一致。
2. **检索层**：保留各路候选与分数，支持离线回放。
3. **生成层**：只消费已授权证据，并把引用映射回来源。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 检索分层诊断

分别报告召回阶段上限、rerank 前后 NDCG、候选数、批大小和模型延迟。

“交叉编码器重排序”的最小测试集应覆盖：

- 已知证据的精确查询；
- 同义表达和术语查询；
- 权限过滤与空结果；
- 重复文档和同分候选；
- 索引版本不一致；
- 精确检索对照及 Recall@K。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。

## 总结与下一篇

- 交叉编码器把 query 与 document 联合编码并输出相关性分数，通常比双编码器精细但计算成本更高。
- 正确实现必须同时定义输入输出、关键状态、失败行为和资源上限。
- 先用小数据验证不变量，再扩大规模衡量质量、延迟、成本和内存。
- AI 工程中的模型决策与真实执行应分层，避免把候选意图当作已完成事实。
