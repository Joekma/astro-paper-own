## 学习导航

**核心问题**：如何让多个任务重叠执行，同时控制资源、顺序和取消传播？本文聚焦“asyncio、Task 与 Future”。

**贯穿场景**：一个 Agent 同时调用搜索、数据库和模型服务，但每个下游都有独立限额。

读完本文，你应该能够：

- 用输入、输出和不变量解释“asyncio、Task 与 Future”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

asyncio 事件循环调度 Task，Future 表示尚未完成的结果；创建 Task 后必须等待、取消或收集其异常。

评估“asyncio、Task 与 Future”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 任务、资源与结果契约

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 任务集合、资源上限、优先级、超时和取消信号         |
| 输出     | 结果流、失败集合、调度状态和资源释放记录           |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“asyncio、Task 与 Future”设计实现前，至少回答四个问题：

1. 任务是 CPU 密集、阻塞 I/O 还是原生异步 I/O？
2. 哪些任务独立，哪些存在先后依赖？
3. 下游允许多少在途请求和单位时间请求？
4. 取消与异常需要传播到哪些子任务？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 调度时序推演

理解“asyncio、Task 与 Future”可以按下面顺序：

1. **建立任务与依赖**：为每项工作分配稳定 ID、预算和结果位置。
2. **受限启动**：通过队列、信号量或执行器控制并发。
3. **收集结果**：按输入顺序或完成顺序处理成功与失败。
4. **清理**：取消不再需要的任务并释放连接、许可和缓冲区。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

create_task 启动两个 I/O 操作，await 在挂起点让其他任务运行；任一 Task 异常都应被调用方观察。

推演“asyncio、Task 与 Future”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“asyncio、Task 与 Future”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“asyncio、Task 与 Future”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 容量、取消与失败传播

遗失后台 Task 会吞掉异常或在关闭时被取消；同步阻塞函数不能直接放在协程热路径。

并发优化要比较总吞吐、排队和尾延迟；启动更多任务并不会增加下游容量，反而可能放大重试与拥塞。

本文场景至少应观察：吞吐、并发数、队列长度、P95 延迟、超时率和取消耗时。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“asyncio、Task 与 Future”接入 AI 系统时，建议分为三层：

1. **调度层**：维护依赖、优先级和并发预算。
2. **执行层**：把阻塞、CPU 和异步任务放到合适执行器。
3. **汇总层**：按任务 ID 合并结果并执行部分失败策略。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 并发故障测试

开启调试并记录 task name、创建位置、状态、异常、取消和未完成任务。

“asyncio、Task 与 Future”的最小测试集应覆盖：

- 零任务和单任务；
- 快慢任务混合；
- 并发上限与队列满；
- 一个子任务异常；
- 总截止时间耗尽；
- 取消后没有遗留任务。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。
