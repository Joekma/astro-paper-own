## 学习导航

**核心问题**：如何在候选空间中找到目标、控制搜索成本并保持结果顺序可解释？本文聚焦“Beam Search 与候选剪枝”。

**贯穿场景**：一个 Agent 需要从工具、计划步骤和检索候选中选择下一步动作。

读完本文，你应该能够：

- 用输入、输出和不变量解释“Beam Search 与候选剪枝”，而不只是复述名词；
- 手工推演一个最小案例，并指出每一步为什么成立；
- 识别复杂度结论背后的前提和不适用边界；
- 给实现设计可观测字段、失败测试和验收条件。

## 先给出结论

Beam Search 每层只保留得分最高的 B 个部分候选，用可控内存近似原本指数级的序列搜索。

评估“Beam Search 与候选剪枝”时，先写清主要操作、数据规模和正确性要求，再讨论库或框架。相同名称在不同实现中可能有不同默认参数，本文只依赖明确写出的机制与契约。

## 问题形式与返回语义

| 项目     | 本文约定                                           |
| -------- | -------------------------------------------------- |
| 输入     | 候选集合、目标条件、代价函数和停止条件             |
| 输出     | 目标位置、排序结果、可行路径或经过剪枝的候选集     |
| 核心状态 | 能解释当前结果如何得到、下一步允许做什么的最小状态 |
| 验证依据 | 小规模期望结果、结构不变量、失败类型和资源上限     |

为“Beam Search 与候选剪枝”设计实现前，至少回答四个问题：

1. 输入是否满足有序、非负权或无环等前提？
2. 未命中、无解和多解分别如何返回？
3. 候选同分时采用什么确定性顺序？
4. 算法承诺精确最优还是有界近似？

这些问题决定了实现是否可测试。只返回最终值而不保留必要诊断状态，会让正确结果与偶然结果难以区分。

## 搜索或排序过程

理解“Beam Search 与候选剪枝”可以按下面顺序：

1. **初始化**：建立边界、前沿、距离、父节点或当前最优候选。
2. **选择下一项**：按算法规则从尚未处理的候选中选取。
3. **更新与剪枝**：扩展合法候选并丢弃已证明无效或劣化的状态。
4. **结束并回溯**：在满足停止条件后构造位置、顺序、路径或无解结果。

这里最容易忽略的是第三步。不变量不是额外文档，而是可以写进断言和测试的正确性条件；一旦不变量被破坏，后续即使输出“看起来合理”，也不应继续信任。

## 逐步推演一个最小例子

每步产生 4 个扩展，beam width=2 时只保留累计分数最高的两个序列，再从它们继续展开。

推演“Beam Search 与候选剪枝”时不要跳过中间状态。建议把过程记成如下审计记录：

```text
输入 → 当前状态 → 应用规则 → 新状态 → 是否满足不变量 → 是否终止
```

如果手算结果与实现不同，先核对输入规范化、边界方向、比较规则和停止条件，再检查性能。很多所谓“算法变慢”其实是重复状态、错误过滤或错误终止造成的工作量放大。

## 实现契约

“Beam Search 与候选剪枝”的实现不应只暴露一个含义模糊的 `run(data)`。更稳妥的接口需要明确：

- 输入记录的标识、类型、单位和版本；
- 输出值的语义以及是否为近似结果；
- 空输入、非法输入和部分失败的行为；
- 可配置预算，例如最大规模、最大步骤或超时；
- 用于复现的参数、随机种子或确定性二级键。

把“Beam Search 与候选剪枝”接入框架时，应把框架调用放在契约外层。核心规则先用小数据验证，再接入远程模型、数据库或消息系统，才能把规则错误与依赖故障分开。

## 复杂度、最优性与剪枝

过小 beam 会过早丢掉后来更优的路径；长度偏置、重复序列和不可比较分数会扭曲结果。

搜索与排序必须同时报告时间、峰值前沿和最优性；启发式减少展开量时，还要测量相对精确基线的质量损失。

本文场景至少应观察：候选数、展开节点数、比较次数、峰值内存和最优性差距。报告任何复杂度或指标时，都要同时写出规模、参数和测试分布。

当数据量很小、规则可直接表达，或无法构造可靠验收集时，优先使用更简单的顺序流程。引入高级结构或近似算法之前，应先证明当前瓶颈确实来自这一层。

## 在 AI 工程中的使用方式

把“Beam Search 与候选剪枝”接入 AI 系统时，建议分为三层：

1. **候选生成**：模型或检索器可以提出候选，但不能改变算法前提。
2. **确定性筛选**：用成本、权限、依赖和预算剪掉不可执行动作。
3. **执行验证**：真实工具执行后把观察写回状态，再决定是否继续搜索。

这种分层能避免把模型输出当作系统事实。局部机制有效，也不代表端到端任务一定改善；还需要用真实任务同时观察质量、延迟、成本与失败分布。

## 算法正确性检查

记录每层候选数、剪枝边界分数、序列长度、重复率和相对穷举的质量差。

“Beam Search 与候选剪枝”的最小测试集应覆盖：

- 空集合、单元素和未命中；
- 已排序、逆序和大量重复；
- 同分时的稳定顺序；
- 不可达或无解状态；
- 最坏输入与预算终止；
- 与穷举或可信实现对照。

上线前再使用接近真实分布的数据做容量测试。测试报告要同时给出输入规模和参数，否则单独的耗时或指标无法比较。

## 常见误区

- **名称代替定义**：没有说明输入、输出和约束，就无法判断两个实现是否在解决同一个问题。
- **局部复杂度代替完整成本**：忽略了查找、预处理、网络、复制或恢复步骤。
- **只测成功路径**：空输入、重复状态和预算终止往往才是生产故障来源。
- **把近似或启发式结果称为保证**：应明确最优性、概率性和误差边界。
- **为了套用 AI 场景而强行调用模型**：确定性规则能完成的工作不应交给不稳定输出。

## 总结与下一篇
