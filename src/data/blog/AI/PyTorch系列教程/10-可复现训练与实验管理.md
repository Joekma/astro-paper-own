## 本篇要解决的问题

设置 `torch.manual_seed(42)` 为什么仍可能得到不同结果？可复现是否意味着跨 PyTorch 版本、CPU 与 GPU 都逐 bit 相同？除了随机种子，一次实验还要保存哪些证据，才能判断两组指标是否可比较？

可复现不是一个布尔开关，而是一组逐层收紧的契约：

```text
代码/配置 → 数据与划分 → 随机数流 → 算子确定性
          → 硬件与版本 → Checkpoint → 指标与日志
```

### 前置知识

已经完成配置、Checkpoint 和断点续训，理解 DataLoader worker 与训练状态。

## 先定义可复现目标

PyTorch 官方明确说明：不能保证不同 release、不同平台，甚至 CPU 与 GPU 之间完全相同。实践中应区分三种目标：

1. **同进程重跑某段代码一致**：用于单元测试和调试。
2. **同环境独立运行落在容差内**：用于实验对比，是最常见目标。
3. **跨机器、跨版本逐 bit 一致**：成本极高，且很多算子无法保证。

项目应声明目标，而不是笼统写“已固定 seed”。本系列默认目标是：在同一代码、数据、PyTorch 版本与设备类型下，独立运行的关键指标落入预先定义的容差；不承诺跨平台权重逐 bit 一致。

## 统一基础随机种子

```python
import os
import random

import numpy as np
import torch


def seed_everything(seed: int) -> None:
    os.environ["PYTHONHASHSEED"] = str(seed)
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)


seed_everything(42)
```

`torch.manual_seed` 会设置 CPU 及当前支持设备的 PyTorch 随机数生成器，但不会控制 Python `random`、NumPy Generator 对象或第三方库。现代 NumPy 代码可能使用独立 `np.random.default_rng(seed)`，它不读取全局 `np.random.seed`，仍要显式传入 seed。

`PYTHONHASHSEED` 最好在启动 Python 进程前设置；运行中修改不能回溯改变已经创建的哈希结构。不要把它误解为 PyTorch Tensor 的随机种子。

## 为不同职责分配 Generator

只使用一个全局随机数流会让无关代码影响训练。例如在模型初始化前新增一次随机可视化，就可能改变所有初始权重。可以为数据划分和 DataLoader 独立创建 Generator：

```python
split_generator = torch.Generator().manual_seed(1001)
loader_generator = torch.Generator().manual_seed(2001)

train_dataset, val_dataset = torch.utils.data.random_split(
    train_full,
    [55_000, 5_000],
    generator=split_generator,
)

train_loader = torch.utils.data.DataLoader(
    train_dataset,
    batch_size=128,
    shuffle=True,
    generator=loader_generator,
)
```

这种分离让“换划分”和“换 batch 顺序”成为两个独立实验变量。更严格的项目会保存实际划分索引，而不只保存生成索引的 seed。

## DataLoader worker 的随机性

多进程加载时，PyTorch 会为 worker 派生种子；Dataset 中若还调用 NumPy 或 Python 随机函数，需要同步初始化：

```python
def seed_worker(worker_id: int) -> None:
    del worker_id
    worker_seed = torch.initial_seed() % (2**32)
    np.random.seed(worker_seed)
    random.seed(worker_seed)


loader_generator = torch.Generator().manual_seed(2001)

train_loader = torch.utils.data.DataLoader(
    train_dataset,
    batch_size=128,
    shuffle=True,
    num_workers=4,
    worker_init_fn=seed_worker,
    generator=loader_generator,
    persistent_workers=True,
)
```

`torch.initial_seed()` 在各 worker 中不同。不能在 `worker_init_fn` 里给所有 worker 固定同一个常量，否则它们可能产生相同增强序列。

`persistent_workers=True` 会让 worker 跨 epoch 保留，随机数流也会继续前进。恢复到 epoch 边界时若要求精确延续，需要保存 DataLoader/Sampler 相关 Generator 状态，或按 epoch 重新派生确定性种子。

## 确定性算法

```python
torch.use_deterministic_algorithms(True)

if torch.cuda.is_available():
    torch.backends.cudnn.benchmark = False
```

`torch.use_deterministic_algorithms(True)` 要求支持的算子选择确定性实现；遇到没有确定性实现的操作时抛错。它帮助暴露问题，但可能降低性能。

cuDNN benchmark 会针对新 Shape 测量多个卷积算法并选择较快实现。硬件噪声可能导致不同运行选择不同算法；关闭 benchmark 有利于稳定选择，但确定性与 benchmark 是不同控制，关闭后也不代表所有算子必然确定。

开发期还可以使用仅警告模式定位范围：

```python
torch.use_deterministic_algorithms(True, warn_only=True)
```

最终实验不应长期忽略警告。要么接受并记录非确定性边界，要么替换算子或设备路径。

## 保存与恢复随机数状态

seed 只定义随机序列起点，Checkpoint 恢复需要回到中断位置：

```python
def capture_torch_rng_state() -> dict[str, object]:
    state: dict[str, object] = {
        "cpu": torch.get_rng_state(),
    }
    if torch.cuda.is_available():
        state["cuda_all"] = torch.cuda.get_rng_state_all()
    return state


def restore_torch_rng_state(state: dict[str, object]) -> None:
    torch.set_rng_state(state["cpu"])
    if torch.cuda.is_available() and "cuda_all" in state:
        torch.cuda.set_rng_state_all(state["cuda_all"])
```

Python 与 NumPy 状态也可以保存，但它们的对象格式需要谨慎序列化，并会影响 `weights_only=True` 的安全加载边界。更简单的教学项目可以保证增强只由 DataLoader 的显式 Generator 驱动，并在 epoch 边界恢复。

恢复顺序很重要：必须在创建下一轮迭代器和执行随机操作之前恢复状态。先做一次随机日志采样再恢复，会让调试代码改变训练轨迹。

## 固定数据证据

相同 seed 不足以证明数据相同。至少记录：

- 原始数据集名称、版本、下载来源和文件哈希；
- 过滤、去重、标签映射和预处理版本；
- 训练、验证、测试的实际样本索引或清单哈希；
- 类别名称与索引顺序；
- Dataset 和 transform 配置。

FashionMNIST 是稳定公共数据集，真实业务数据却可能持续更新。如果一次实验的数据快照已不可访问，精确复现通常也不可能。

可以保存划分索引：

```python
split_manifest = {
    "train_indices": train_dataset.indices,
    "val_indices": val_dataset.indices,
}
torch.save(split_manifest, "runs/run-001/split.pt")
```

数据量很大时保存标识列表或内容哈希，不必复制全部原始数据。

## 建立运行清单

每次训练创建独立目录：

```text
runs/20260809-013000-fashion-mlp/
├─ config.json
├─ environment.json
├─ split.pt
├─ metrics.jsonl
├─ checkpoints/
│  ├─ latest.pt
│  └─ best.pt
└─ tensorboard/
```

环境清单可以记录：

```python
import json
import platform
import sys
from pathlib import Path


def write_environment(path: Path) -> None:
    environment = {
        "python": sys.version,
        "platform": platform.platform(),
        "torch": torch.__version__,
        "cuda_runtime": torch.version.cuda,
        "cudnn": torch.backends.cudnn.version(),
        "device": torch.cuda.get_device_name(0)
        if torch.cuda.is_available()
        else "cpu",
    }
    path.write_text(
        json.dumps(environment, ensure_ascii=False, indent=2),
        encoding="utf-8",
    )
```

还应记录代码提交标识。工作区有未提交修改时，要保存 diff 或明确标记 dirty；只有 commit hash 而忽略本地改动，会产生虚假的可复现性。

## 结构化指标与 TensorBoard

终端输出适合观察，不适合后续比较。JSON Lines 每行保存一个事件：

```python
def append_metrics(path: Path, record: dict[str, object]) -> None:
    with path.open("a", encoding="utf-8") as file:
        file.write(json.dumps(record, ensure_ascii=False) + "\n")


append_metrics(
    run_dir / "metrics.jsonl",
    {
        "epoch": epoch,
        "global_step": global_step,
        "train_loss": train_metrics["loss"],
        "val_loss": val_metrics["loss"],
        "val_accuracy": val_metrics["accuracy"],
        "learning_rate": optimizer.param_groups[0]["lr"],
    },
)
```

TensorBoard 提供曲线和分布可视化：

```python
from torch.utils.tensorboard import SummaryWriter

writer = SummaryWriter(log_dir=run_dir / "tensorboard")
writer.add_scalar("loss/train", train_metrics["loss"], epoch)
writer.add_scalar("loss/validation", val_metrics["loss"], epoch)
writer.add_scalar("accuracy/validation", val_metrics["accuracy"], epoch)
writer.add_scalar("optimization/lr", optimizer.param_groups[0]["lr"], epoch)
writer.flush()
```

训练结束或异常退出时调用 `writer.close()`。不要每个 step 记录所有参数直方图；日志 I/O 和事件文件体积也会影响训练。

## 用容差比较而不是迷信小数点

两次实验差异要与随机波动和指标分辨率比较。一个验证集只有 5,000 个样本，准确率改变 0.0002 就只对应一个样本。单次提升几个万分点通常不足以支持结论。

更稳妥的比较包括：

- 固定数据划分，使用多个独立 seed；
- 报告均值、标准差和每次结果；
- 预先定义主要指标与容差；
- 同时观察训练成本、收敛速度和失败运行；
- 不从多个指标中只挑最有利的一项。

可复现是让差异可解释，不是消除所有随机性。若生产目标本身对 seed 极度敏感，应把敏感性作为模型风险报告。

## 常见误区

- **只设置 `torch.manual_seed`**：Python、NumPy、worker 和独立 Generator 仍可能随机。
- **同 seed 保证跨平台逐 bit 一致**：框架版本、硬件与算子实现都可能不同。
- **确定性没有代价**：某些确定性实现更慢，部分算子甚至不提供。
- **commit hash 足够描述代码**：未提交修改会被遗漏。
- **数据集名称足够描述数据**：版本、过滤、划分和类别映射同样重要。
- **单次最佳结果能证明改进**：需要多 seed 和预先定义的比较方法。

## 本篇自检

1. 为什么 seed 相同仍不等于跨设备完全一致？
2. DataLoader worker 为什么不应全部设置同一个固定 seed？
3. 为什么保存实际划分索引比只保存划分 seed 更稳妥？

<details>
<summary>查看答案</summary>

1. 不同设备、库版本和并行算子可能采用不同数值顺序或非确定性实现。
2. 相同 seed 会让多个 worker 生成重复随机序列，降低增强多样性并造成相关错误。
3. 算法、数据顺序或版本变化时，同 seed 未必产生同一划分；索引直接定义了成员关系。

</details>
