## 概述

使用 Git 访问 GitHub 时，可能遇到类似错误：

```text
Failed to connect to github.com port 443 after 21090 ms: Couldn't connect to server
```

端口 443 是 HTTPS 默认端口。这个错误不一定是“Git 端口和系统端口不一致”，更常见原因是代理配置、DNS、网络防火墙、TLS 拦截、远程地址或 GitHub 连通性问题。

## 先确认远程地址

```bash
git remote -v
```

如果远程地址是 HTTPS：

```text
origin  https://github.com/username/repo.git (fetch)
origin  https://github.com/username/repo.git (push)
```

则访问会走 HTTPS 443。若使用 SSH 地址：

```text
git@github.com:username/repo.git
```

则通常走 SSH 22，或配置后走 443 的 SSH 入口，排查方式不同。

## 基础连通性检查

```bash
# 检查 DNS
nslookup github.com

# 检查 HTTPS 响应
curl -I https://github.com

# 查看 Git 访问细节
GIT_CURL_VERBOSE=1 git ls-remote https://github.com/username/repo.git
```

Windows PowerShell 中可以使用：

```powershell
Test-NetConnection github.com -Port 443
```

如果浏览器也无法访问 GitHub，应先排查系统网络、代理、DNS 或公司防火墙。

## 使用代理时的配置

当你使用 VPN 或本地代理工具时，需要确认 Git 使用的代理协议和端口。

### HTTP 代理

```bash
git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890
```

注意：即使访问的是 HTTPS，很多本地代理仍然使用 `http://127.0.0.1:端口` 作为代理地址。这里的协议表示“连接代理服务器的协议”，不是目标网站协议。

### SOCKS5 代理

```bash
git config --global http.proxy socks5h://127.0.0.1:7890
git config --global https.proxy socks5h://127.0.0.1:7890
```

`socks5h` 表示域名解析也交给代理处理，常用于本地无法正确解析目标域名的场景。

### 只针对 GitHub 配置代理

```bash
git config --global http.https://github.com.proxy http://127.0.0.1:7890
```

Git 的 URL 级配置使用 `http.<url>.proxy` 形式；不要写成不存在的 `https.https://github.com.proxy`。

## 查看与取消代理

查看配置来源：

```bash
git config --global --show-origin --get-regexp 'http.*proxy'
git config --system --show-origin --get-regexp 'http.*proxy'
git config --local --show-origin --get-regexp 'http.*proxy'
```

取消全局代理：

```bash
git config --global --unset http.proxy
git config --global --unset https.proxy
```

取消 GitHub 专用代理：

```bash
git config --global --unset http.https://github.com.proxy
```

如果命令提示 key 不存在，说明当前作用域没有这项配置。

## DNS 缓存与系统代理

刷新 DNS 有时可以解决解析缓存问题，但它不是所有 443 错误的通用解法。

```bash
# Windows
ipconfig /flushdns

# macOS
sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder

# systemd-resolved Linux
sudo resolvectl flush-caches
```

旧系统可能使用：

```bash
sudo systemd-resolve --flush-caches
```

还要确认 Git 所在终端是否继承了环境变量：

```bash
env | grep -i proxy
```

Windows PowerShell：

```powershell
Get-ChildItem Env:*proxy*
```

环境变量如 `HTTP_PROXY`、`HTTPS_PROXY` 也会影响部分工具。

## TLS 或证书问题

如果错误中出现证书、SSL、CA 字样，不要直接关闭校验：

```bash
git config --global http.sslVerify false
```

这会削弱安全性，不建议作为解决方案。更合理的做法是：

- 更新 Git 和系统证书。
- 检查公司代理是否做 TLS 检查。
- 将公司根证书按组织规范导入可信证书库。
- 确认系统时间正确。

## HTTPS 与 SSH 的替代方案

如果 HTTPS 长期受限，可以改用 SSH：

```bash
git remote set-url origin git@github.com:username/repo.git
ssh -T git@github.com
```

如果网络只允许 443，也可以按 GitHub 的 SSH over HTTPS 文档配置 SSH 走 `ssh.github.com:443`。这属于 SSH 配置问题，不应和 HTTPS 代理混为一谈。

## 排查速查表

| 场景 | 检查点 | 常用命令 |
|------|--------|----------|
| 使用本地代理后失败 | Git 是否配置了正确代理协议和端口 | `git config --global --get http.proxy` |
| 不使用代理也失败 | 是否残留代理配置 | `git config --show-origin --get-regexp 'http.*proxy'` |
| 只有终端失败 | 环境变量或 Git 配置不同 | `env | grep -i proxy` |
| DNS 异常 | 域名是否能解析 | `nslookup github.com` |
| 公司网络失败 | 防火墙或 TLS 检查 | `curl -I https://github.com` |
| HTTPS 始终不可用 | 尝试 SSH 远程地址 | `ssh -T git@github.com` |

## 推荐排查流程

```bash
# 1. 确认远程地址
git remote -v

# 2. 检查 Git 代理配置
git config --show-origin --get-regexp 'http.*proxy'

# 3. 检查系统环境变量
env | grep -i proxy

# 4. 检查 GitHub 连通性
curl -I https://github.com

# 5. 对目标仓库做只读测试
GIT_CURL_VERBOSE=1 git ls-remote https://github.com/username/repo.git
```

Windows 用户可把第 3 步替换为：

```powershell
Get-ChildItem Env:*proxy*
```

## 小结

GitHub 443 连接失败的核心是定位网络路径：远程地址决定协议，代理配置决定流量出口，DNS 和防火墙决定能否到达目标，TLS 配置决定能否建立安全连接。先定位是哪一层失败，再修改对应配置，会比反复切换代理更可靠。
